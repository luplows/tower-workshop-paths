**OQ-19. Let the Path list include the same upgrade multiple times**

**OQ-7. Implement batch buying**
As a player, I want the recommended buy order to reflect how I actually purchase in-game (multiple levels at once), so that the steps match real button presses.
`getCheapestNextUpgrades` (OQ-17/OQ-19) now ranks by batch cost, not single-level cost: 100 levels at a time for a Workshop upgrade with more than 1000 max levels, 10 for one with at least 10, or 1 for one with fewer than 10 max levels in the first place (Multishot Targets, Bounce Shot Targets, Orbs — caught in review; missed in the first pass) — see `Project-Outline.md`. Still Workshop-only (Enhancements aren't batched). **Correction from the original framing:** the game doesn't actually require buying in these batches — single-level purchases remain available in-game too — this tool just always expresses the Path list's recommendations in these fixed batch sizes for practicality; `README.md`, `Project-Outline.md`, and the code comments were reworded to not overstate this as a game restriction. Each ranked entry gained a `levels` field (the batch size actually used) alongside `currentLevel`/`nextLevel`, which now jump by that many levels instead of always by 1. **Resolved the open partial-batch question:** a batch shrinks to whatever's left when fewer than a full batch remain before max level (e.g. an upgrade 4 levels from max with a 10-level batch size buys those final 4) — the only case a batch is ever shrunk. If any level within a (max-trimmed) batch has no valid cost data, the whole batch is refused and the upgrade lands in `unknownCost` rather than pricing a partial one, since a real near-max partial batch and a data gap aren't the same situation. Confirmed the ranking math genuinely changes, not just presentation: at level 0, the previous single-level cheapest-first order (led by several upgrades tied at cost 30) is replaced by one led by Multishot Targets' 1-level batch (cost 450, since its max level is only 7). Rewrote `cheapestNextUpgrades.test.js`'s existing scenarios for batch semantics, added dedicated tests for the sub-10-max-level batch size, partial-batch trimming, and batch-refused-on-data-gap, and updated `UpgradePath`'s tests (unit, component, e2e) to match.
**Resolved in:** [#38](https://github.com/luplows/tower-workshop-paths/pull/38) (tracked since [#28](https://github.com/luplows/tower-workshop-paths/pull/28)).

**OQ-29. Add Workshop Enhancements to the Path list**
As a player, I want the Path list to recommend Enhancements alongside Workshop upgrades, so that it's a single ranked source of "what's cheapest right now" instead of only covering half of what I might buy.

**OQ-5. Respect Workshop upgrade-unlock gates**
As a player who hasn't unlocked every Workshop upgrade group yet, I want the buy-order algorithm to skip upgrades I can't buy, so that it never recommends something unavailable to me.
`tower-idle-toolkit`'s `ATTACK_UNLOCKS`/`DEFENSE_UNLOCKS`/`UTILITY_UNLOCKS` (a new `workshopUnlockGroups.js` re-exports them keyed by category id, matching `WORKSHOP_CATEGORIES`) give every tree an ordered list of groups: a free "Default" group plus several paid ones, each gating a handful of upgrades behind a one-time coin cost (e.g. Attack's "Multishot Upgrades" group, 400 coins, unlocks "Multishot Chance" and "Multishot Targets") — confirmed 1:1 against every Workshop upgrade, no gaps or overlaps. Resolved the open design question from this story in favor of the same approach already used for the Enhancements Lab (OQ-31) and its per-tree gate (OQ-6): a not-yet-purchased group's upgrades are excluded from `getCheapestNextUpgrades` entirely, and the group's own one-time unlock cost competes as its own Path candidate instead (`source: 'unlock'`, shown as "Unlock: {group name}" — needed since a group's name can collide with a plain upgrade name, e.g. "Death Defy" is both), rather than a separate manual step outside the algorithm. **A tree's paid groups must be bought in order** (a real game rule, corrected after initial review — the first version let any locked group be bought independently): `nextPurchasableGroup` walks each tree's group list from the start and returns the earliest not-yet-purchased one, so only that single group is ever offered as an unlock candidate or an inline unlock button — every later group's upgrades show a "Locked until "{that group}" is unlocked" note instead of their own unlock option, even though they gate unrelated upgrades (e.g. Defense's "Thorn Upgrades" can't be bought before "Defense Upgrades"). **OQ-2. Implement the core, priority-weighted buy-order algorithm**
As a player, I want the app to recommend which Workshop upgrade or Enhancement to buy next according to my priorities, so that I know how to spend my coins efficiently even when the cheapest option isn't what I value most.
The tool's actual core feature — one combined ranked list spanning both Workshop upgrades and Enhancements, not two separate paths, per the design decided when this story was still open. `getPrioritizedNextUpgrades` (`src/utils/cheapestNextUpgrades.js`) replaced `getCheapestNextUpgrades` (OQ-17/OQ-29's cost-only placeholder) as the Upgrade Path screen's actual ranking; the cost-only function itself stays in the codebase, unused by the UI but still exercised by its own test file, since its tests are the main regression coverage for the batching/gating plumbing (`buildCandidateCursors`/`nextBatchCost`) both functions share.
Implements the formula from `Project-Outline.md`'s "Core Feature: Recommended Buy Order" (`score = ratio × (base's next cost ÷ this item's next cost)`), using OQ-3's finalized priority data: the eHP set's 6 named Enhancement ratios, and FALLBACK_RATIO (1/128) for every Workshop upgrade and unranked Enhancement category (`src/data/enhancementPriority.js`). The formula's `base`, Coin Bonus, is itself a gated/capped Enhancement category, so `resolveBaseCost` resolves what stands in for it each scoring pass: Coin Bonus's own live cost while normal; once maxed, a re-anchor to whichever ranked item is currently purchasable (live each pass); and, while locked (which covers "before the Enhancement Lab is bought" too, not just "Lab bought but Utility tree under its 50B threshold" — both are just different points along the same chain), the *effective cost of reaching Coin Bonus's own first level* — the Lab's remaining cost + every Cash Bonus level still needed to cross the threshold + Coin Bonus's own real level-1 cost. Whichever prerequisite is next in that chain (the Lab, or else Cash Bonus) scores exactly 1 via `criticalPathKey`, the same self-referential score the base always gets against itself — not competing on its own flat cost, since it's a required step toward the ratio-1 item, not a purchase valued on its own merits. A cheap-enough Workshop upgrade still wins until its own cost approaches that effective cost (scaled by FALLBACK_RATIO); past that, the chain toward Coin Bonus starts winning instead — falling back to plain cheapest-cost ranking only in the truly degenerate case nothing ranked, and no prerequisite toward it, is reachable at all, which is mathematically equivalent for same-ratio items regardless of what the anchor's value would have been.
This locked-case design was corrected twice after initial review. First: the original version priced the "locked" stand-in as just the coins still needed to cross the threshold, ignoring the Lab's cost entirely and undervaluing the whole chain relative to Workshop upgrades — the Lab would barely ever get recommended. The effective-cost/critical-path model replaced it. Second: whether Coin Bonus is *still* locked was being read from the caller's real `enhancementLevels` only, same as every other gate in this file — but unlike those, a single simulation run can realistically cross this one entirely on its own (10 simulated Cash Bonus purchases, well inside the 50-row cap), and Cash Bonus's `criticalPathKey` override scores it 1 regardless of its real cost, so nothing else ever revisited the check once crossed — the reported bug was 50 straight "Cash Bonus +" rows from a fresh Lab-just-bought state instead of exactly 10. Fixed by reading Cash Bonus's live cursor level (this run's own simulated progress) instead of the static entered level for that one check.
Ties are broken first by the eHP set's own priority order, then alphabetically by name — the same final tie-break the cost-only function already used. Batching, the row cap, `unknownCost` reporting, and every existing gate (Workshop unlock groups OQ-5, the Enhancement Lab OQ-31, the per-tree spend threshold OQ-6) are unchanged, reused via the same shared cursor-building helper as before.
**Still open, tracked separately:** OQ-1 (Workshop cost data isn't individually spot-checked yet) is a refinement on top of this, not a blocker to shipping it — this story is specifically about the ranking logic itself, given whatever cost/priority data currently exists.
**Resolved in:** [#54](https://github.com/luplows/tower-workshop-paths/pull/54), corrected in [#56](https://github.com/luplows/tower-workshop-paths/pull/56).

**OQ-41. Cut the unit-test suite's jsdom overhead**

**OQ-40. Guard the UI's appearance against regressions**
As a player, I want the layout to keep working as features are added, so that a change to one screen doesn't silently break how another one looks.
Removing the pre-merge visual-inspection gate traded a human spot-check for automated coverage, but the automated side only covered *behavior* — a CSS or layout break passed CI silently. Closed with six `toHaveScreenshot()` assertions in `e2e/appearance.spec.js`: Upgrade, Path and Enhance, each at a 1280x720 desktop viewport and a 390x844 mobile one. **How many viewports** (one of the story's open questions): two, and only two, because these ride the same required status check as the rest of the e2e suite, so a flaky baseline blocks every PR in the repo. The mobile column earns its churn by crossing `index.css`'s 1024px breakpoint, where the root font drops to 16px and `#root` stops being a 480px column — a genuinely different layout, not the same one scaled — which partly de-risks OQ-9 without substituting for a real device. Shots are viewport-sized rather than `fullPage`: the Path list is ~4800px tall, and a baseline that size churns on any ranking change far below the fold while adding nothing a CSS break would show.
**Decided — baselines are generated by CI, never locally.** `.github/workflows/update-screenshots.yml` mints them on a runner, verifies they reproduce by re-running the whole e2e suite against them, and commits them to the branch. It runs with `--update-snapshots=missing`, which can only give a *newly added* screenshot its first baseline and never rewrites an existing one, so the job structurally cannot turn a regression green (`REVIEW.md` item 10); rewriting baselines for an intentional appearance change is a manual dispatch with `mode=all`, or deleting the stale images in the PR. Two implementation notes worth not rediscovering: a `workflow_dispatch` workflow **cannot be dispatched until its file is on the default branch**, which is why the job also triggers on `pull_request` — otherwise a PR that adds a screenshot could never generate its own baselines; and a push made with `GITHUB_TOKEN` **does not start further workflow runs** (GitHub files the bot's own push as `action_required` and never runs it), so the CI run that checks a freshly-committed baseline is the one started by the *next* push.
**Pixel tolerance** (the story's other open question), measured rather than guessed: `threshold: 0.05` and `maxDiffPixelRatio: 0.0005`. Playwright's default `threshold: 0.2` turned out to be nearly colour-blind — shifting `--accent` from `#aa3bff` to `#6b3bff`, an obviously different purple, was reported as *zero* differing pixels; 0.05 catches it and still reports zero differing pixels run-to-run on an unchanged app. The ratio allows 460 px of a 1280x720 shot and 164 px of a 390x844 one, against 773-980 px for the smallest deliberate break tried (one 12px tab label bumped to 13px) and 3424-19905 px for 1px of extra header padding.
**The local-vs-CI renderer gap was real but far smaller than assumed.** The premise for generating baselines in CI was that a Claude Code web session's pre-installed chromium (141) renders differently from the build CI downloads (153). Measured at zero tolerance, the two differ by **48 pixels** on four of the six shots and not at all on the other two — all of it sub-threshold antialiasing on a single word in the category tab bar — so CI's baselines do in fact pass in a web session. The CI-generated rule stands anyway: it costs nothing, it is the only version that is guaranteed to match whatever compares against it, and another OS's font stack would not be nearly so close. `playwright.config.js` drops Playwright's default `{projectName}`/`{platform}` suffixes from `snapshotPathTemplate` for the same reason — a machine that does render differently then fails loudly instead of quietly minting a second, parallel baseline set and passing against it.
**Resolved in:** [#83](https://github.com/luplows/tower-workshop-paths/pull/83).

**OQ-44. Guard the dark palette's appearance too**
As a player who uses dark mode, I want the dark theme to keep looking right as features are added, so that a palette that drifts out of sync doesn't ship unnoticed.
OQ-40's screenshots pin `colorScheme: 'light'` deliberately — a runner or agent machine with a dark OS preference would otherwise render a different app and produce baselines nobody meant. That leaves the dark palette unguarded, and it is the half more likely to drift: `index.css` carries the dark values **twice** (once under `prefers-color-scheme: dark`, once under `:root[data-theme='dark']`, because a selector list cannot span in and out of a `@media` block) with only a comment asking that they be kept in sync.
**Decided — a unit test, not a full screenshot matrix, for the realistic failure.** The failure this story is actually about is those two blocks drifting apart. `src/index.css.test.js` parses both blocks straight out of the stylesheet and asserts they declare the same custom properties with the same values — checked first against the real file, where they turned out **not** to have drifted (byte-identical aside from indentation). For that specific bug a unit test beats a screenshot: instant, catches a sub-pixel/sub-threshold color difference a screenshot's tolerance would miss, and fails naming the exact property (e.g. `--accent`) instead of a pixel count. A unit test can't catch a real browser failing to apply either selector at all, though, so exactly **one** dark screenshot was added — the Path screen at 1280x720 (the richest in `var(--...)` usage: tree/success/danger accents over text/bg/border) — rather than OQ-40's full three-screens-by-two-viewports matrix; dark and light differ only in color, not layout, so the mobile breakpoint that earns its churn in the light matrix (OQ-9) buys nothing extra here.
**Decided — the `data-theme` override paths are in scope.** `header-menu.spec.js` and `App.test.jsx` both already check that the theme toggle sets the `data-theme` *attribute*; nothing checked that index.css's override selectors actually apply it in a real browser. Two Playwright tests read the live computed `--bg` custom property instead of taking a screenshot: forcing `data-theme="dark"` under an OS-light preference must reproduce the same background as OS-dark alone renders, and forcing `data-theme="light"` under OS-dark must suppress it back to the OS-light background. Self-referential on purpose (does forcing a theme reproduce what that theme's own OS preference renders) rather than a hard-coded hex, so it doesn't duplicate the palette values the unit test already guards.
**Resolved in:** [#85](https://github.com/luplows/tower-workshop-paths/pull/85).

**OQ-43. Detect game-patch data drift on a schedule**
As a player, I want the tool's costs to stay correct after the game patches, so that a stale cost table doesn't quietly make every recommendation wrong.
`npm run verify:workshop-costs` already existed as the drift detector; the gap was only that it ran when someone remembered to. `.github/workflows/detect-drift.yml` now runs it automatically, plus `workflow_dispatch` so it can be triggered on demand (the same pattern `update-screenshots.yml` established — and it hit that workflow's same bootstrapping limit: `workflow_dispatch` can't actually be dispatched until the file lands on `main`).
**Decided — weekly cadence.** Game patches are irregular (weeks to months apart) and mytower.app is a small fan site, not an API meant for bulk traffic. Daily would hit it for essentially nothing; monthly risks a patch sitting undetected for most of a month. Weekly (Mondays) bounds staleness to at most a few days at the cost of one scrape a week — the same politeness bar the script's own single-browser-context, delay-between-navigations design already set for a manual run.
**Decided — notify only, never auto-fix.** On confirmed drift the workflow opens (or comments on an existing) GitHub issue with the actual mismatch details; it never opens a PR with regenerated data or touches `src/data/workshopLevels.js` itself. Auto-regenerating shipped data unattended means a bad scrape (or a mytower.app markup change the script misreads) could silently overwrite good, correct data with nobody watching before it ships — the failure mode this story exists to catch, reintroduced one layer up. An issue is the one output that both fails informatively and cannot act destructively without a human reading it first.
**Decided — a failed fetch is not decided drift.** `verify-workshop-costs.mjs` gained an explicit exit-code contract (`exitCodeForResults`, unit tested): 0 clean, 1 when the check itself couldn't complete (a scrape/network problem), 2 for a confirmed `MISMATCH`/`MAX LEVEL DRIFT`. Only exit 2 opens an issue; exit 1 gets one automatic retry (transient blips resolve more often than not) and then just fails the workflow run — visible via GitHub's own Actions failure notification, `review-gate.yml`'s existing mechanism for making a block noticeable — without filing an issue for something that was never confirmed to be a real data problem.
**Decided — Enhancement data is a separate story.** `src/data/enhancementLevels.js` has no verify script today (only the full-resync `extract:enhancement-data`), so extending the same drift treatment to it is out of scope here. Filed as [OQ-45](Open-Questions.md).
**Resolved in:** [#92](https://github.com/luplows/tower-workshop-paths/pull/92).

**OQ-42. Add automated, merge-gating review to pull requests**
As someone working on this project, I want every PR to get an adversarial read of its diff before it merges, so that a green CI check isn't the only thing between a change and `main` — and so that an agent handed a task can be confirmed to have followed the whole defined process, every time.
Removing the pre-merge visual-inspection gate left CI as the sole quality signal on every PR, and CI only knows what the tests already assert: it cannot flag a plausible-looking bug that no test covers, nor a skipped step in the project's own workflow. What shipped is a gate whose *enforcement* never calls Claude and whose *judgement* always does, deliberately split so that neither half can fail silently into the other.

**Decided — a required status check, not a pre-push step.** Review had to be unskippable. A pre-push step runs when someone remembers, and agent sessions only run it if their prompt happens to say so. `.github/workflows/review-gate.yml` sets a `review/agent` commit status to pending when a PR opens or gains a commit; a reviewer agent posts a marker comment (`<!-- agent-review head=<40-char-sha> verdict=pass|fail -->`); the workflow parses it and sets the status. Requiring that context in branch protection is what makes it a gate.

**Decided — commit statuses rather than PR reviews.** GitHub forbids approving your own pull request, which deadlocks a review-based gate on a single-account project where author and reviewer share an identity. Commit statuses carry no such restriction. This is the platform fact the whole design rests on.

**Decided — three properties worth keeping.** A new head commit resets the status to pending, which makes "no dismissal mechanism" a platform guarantee rather than a convention: a verdict cannot outlive the commit it was about. Forgetting to run the reviewer leaves the status pending, so the PR cannot merge — the gate fails safe rather than silently passing. And a marker is honoured only from a commenter with write access (anyone can comment on a public repo) and only when its SHA matches the current head.

**Decided — independence comes from context isolation, not model diversity.** A reviewer sharing the author's *context* knows what the change intended and so cannot see that the diff does something else; a reviewer merely sharing the author's *model* can still re-derive from the artifact. A fresh session supplies that isolation structurally. The real mitigation for shared priors is the enumerated checklist in [`REVIEW.md`](REVIEW.md), which decorrelates by giving the reviewer criteria rather than taste. Running review on a different model remains an untried cheap hedge.

**Decided — no dismissal mechanism, bounded at 2 rounds.** Severity tiers were rejected because they put the blocking decision inside the system being checked; an acknowledgement protocol was rejected because it lets an agent clear a finding with words rather than work. The only way past a `fail` is a commit, which resets the gate. After two rounds the agent states its position, applies `review-blocked` and escalates to a human. A blocked PR blocks its own merge only — agents keep working.

**Decided — circuit breaker at 5 blocked PRs, with exemptions.** Once five open PRs carry `review-blocked`, something systemic is wrong and landing more only spreads it. Critically, **a tripped breaker narrows what may land rather than stopping landing outright**: the PR that fixes the jam stays landable via a `breaker-override` label or a diff confined to `.github/workflows/`, or the breaker becomes a trap escapable only by admin merge. Neither exemption skips review.

**Decided — a scheduled sweep merges, not the author.** Landing was briefly the author's job, which assigned it to a session that no longer exists by the time its verdict arrives: [#92](https://github.com/luplows/tower-workshop-paths/pull/92) sat merge-ready with nobody responsible, and [#93](https://github.com/luplows/tower-workshop-paths/pull/93) only landed because a human asked. `.github/workflows/land-approved.yml` now lands the oldest ready PR on a schedule, **one per run** — every ready PR was verified against the `main` that existed before the sweep, and GitHub recomputes `mergeable_state` asynchronously, so a second merge in the same run would be decided on a value read before the first one landed. Letting the *reviewer* merge was rejected for collapsing judging and acting into one hand.

**The Claude Code Action never worked, and was deleted.** `.github/workflows/review.yml` returned `401 OAuth access token is invalid` for every `claude setup-token` OAuth token, retried ten times at zero cost; two independently generated tokens failed identically, ruling out a bad paste ([action#1614](https://github.com/anthropics/claude-code-action/issues/1614), open, no workaround). Three things worth not rediscovering: `github_token` must be passed alongside `claude_code_oauth_token` or the action attempts GitHub App auth first and 401s before reaching the model ([action#721](https://github.com/anthropics/claude-code-action/issues/721)); the action suppresses its own error text unless `show_full_output: true`, which prints model output into a public log; and `continue-on-error` made a total failure report a **green** check, which is worse than a red one, since "reviewed fine" and "did not run" became indistinguishable. It was gated behind `REVIEW_ENABLED` (default off) and then removed entirely once the gate was routed around it. **To restore it:** `git show 44b8afa:.github/workflows/review.yml > .github/workflows/review.yml`, or `git log --all -- .github/workflows/review.yml` to find any version. It would be rebuilt differently now regardless — judgement comes from a spawned reviewer session with an explicit checklist, which is a better arrangement than one Action doing both halves.

**Operational findings that cost real time.** A spawned reviewer does **not** reliably inherit GitHub write access; pre-authorising `add_repo` with `access: "push"` via `extra_allowed_tools` at spawn is what fixes it, and a reviewer that cannot comment cannot clear the gate. A spawned session must be told never to call `AskUserQuestion` — with no human attached that is a hang, not a degraded path. Sessions can die at $0 on a usage limit before doing any work, so "spawned" never implies "ran". The gate originally subscribed to `issue_comment: [created]` only, so a reviewer that posted its review and edited the marker in afterwards was silently ignored, leaving a PR pending with a valid verdict visible on it — fixed by subscribing to `[created, edited]`. And the `/search/issues` API is unavailable to session tokens, so the `SessionStart` hook must use the repo-scoped `/repos/{owner}/{repo}/pulls` endpoint and filter labels client-side.

**The standing test that branch protection still enforces.** On any PR with CI green and `review/agent` pending, `mergeable_state` must read `blocked`. When that context was not required, the identical state read `unstable` — `unstable` means a *non-required* check is outstanding. This matters because the requirement silently went missing once, between being set one evening and being checked the next morning.

**Spawn prompts live in files, and are read end to end before use.** [`.claude/reviewer-prompt.md`](.claude/reviewer-prompt.md) and [`.claude/worker-prompt.md`](.claude/worker-prompt.md) exist because an improvised prompt is never reviewed: the one that launched the OQ-43 worker asserted `review/agent` was already a required check and that its PR would be blocked, neither of which was true then. The sharper lesson came later — a spawn prompt that gains one fix per failed run can end up **injection-shaped**. After three reviewer sessions failed on credentials and one hung on a question, the prompt had accumulated instructions to hunt for tokens on disk *and* to raise questions with nobody, and the next reviewer correctly refused the task as suspicious. Each addition was locally reasonable; nobody had re-read the whole. The fix is to remove what is actually suspicious, never to add reassurance that the task is legitimate — that sentence is what a real injection would say, and a reviewer trained to accept it has lost a defence worth keeping.

**Evidence the gate works.** Two `verdict=fail` results, both real. One caught a circuit breaker reimplemented without the exemption this very story had already mandated — which, combined with the same PR removing manual author merging, would have deadlocked the repository at five blocked PRs with admin merge the only escape. The other caught a PR body that still described the pre-fix version of its own change. Both were missed by an author who had the relevant rules open while writing. The 2-round bound then fired on [#96](https://github.com/luplows/tower-workshop-paths/pull/96) and forced escalation to a human rather than letting the author iterate indefinitely.

**Left open deliberately**, as [OQ-47](Open-Questions.md) (check the block rate once ~20 PRs have been gated) and [OQ-48](Open-Questions.md) (nothing automatically applies `review-blocked` or enforces the 2-round bound, since the automation for it lived in the deleted `review.yml` and never ran). Also unclosed by design: **self-marking**. The orchestrator spawns the reviewer and that verdict clears the orchestrator's own work. The gate guarantees a verdict exists bound to the current commit; it cannot guarantee the verdict was earned. Closing that needs a second GitHub identity, not a better prompt.
