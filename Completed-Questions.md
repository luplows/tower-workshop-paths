**OQ-13. Confirm Workshop upgrade max levels for the current patch**
As a player, I want the max level shown/enforced for each Workshop upgrade to match the current patch, so that `UpgradeLevelInput`'s hard cap never blocks a valid entry or accepts an invalid one.
`tower-idle-toolkit`'s `quantity` values for the ~40 Workshop upgrades are accepted as correct for the current patch. Five were confirmed to differ from the toolkit's shipped defaults and are corrected via `WORKSHOP_QUANTITY_OVERRIDES` (`src/data/workshopQuantityOverrides.js`) rather than editing the third-party package: Rend Armor Chance (299), Health (6000), Health Regen (6000), Recovery Amount (300), Max Recovery (500). A Vitest snapshot test (`workshopCategories.test.js`) guards against upstream structural drift — a `tower-idle-toolkit` update that silently adds/removes/reorders an upgrade or changes a quantity fails CI with a reviewable diff instead of passing unnoticed; updating the snapshot (`vitest -u`) should always be a deliberate, reviewed choice.
**Resolved in:** [#13](https://github.com/luplows/tower-workshop-paths/pull/13).

**OQ-14. Add the Workshop Enhancements input screen**
As a player, I want to enter my current level in every Workshop Enhancement category, the same way I do for base Workshop upgrades, so that Enhancements can eventually feed into the buy-order algorithm too.
A top-of-screen "Upgrade"/"Enhance" mode tab bar (matching the in-game button labels, `ModeTabBar`) switches between the existing Workshop upgrade screen and an Enhancements screen (`EnhancementInputs`, `src/data/enhancementCategories.js`), sharing the same three-tree tab layout (bottom tabs read just "Attack"/"Defense"/"Utility" on both screens) and per-item level input, persisted separately (`enhancementLevels` in `localStorage`, distinct from `workshopLevels` since several category names overlap, e.g. "Damage", "Health"). The 18 categories, their unlock-threshold values (`unlocksAt`, used by OQ-6), and their max level (`quantity`) are hard-coded in `enhancementCategories.js` from the community Google Sheet's Master Sheet tab (column W, "Max level") since `tower-idle-toolkit` has none of this data — these max levels are accepted as correct for the current patch, the same as OQ-13's Workshop values. Levels are hard-capped at `quantity` the same way Workshop upgrades are. Since there's no in-game way to see an Enhancement's current *level* (only its resulting value), the screen also shows a computed value (`src/utils/enhancementValue.js`, `value = (level × 0.01) + 1`, e.g. "1.40×") next to each level input, letting the user cross-check their entry against what they see in-game; Workshop upgrades intentionally show no such value, since too many other multipliers apply there for a raw computed value to be meaningful. A Vitest snapshot test (`enhancementCategories.test.js`, mirroring OQ-13's) guards this hand-transcribed data the same way.
**Resolved in:** [#27](https://github.com/luplows/tower-workshop-paths/pull/27).

**OQ-15. Fix spurious `.snap` file "modified" status on Windows**
As a maintainer, I want `git status` to only show real changes, so that a false positive doesn't get mistaken for actual snapshot drift or mask a real one.
`core.autocrlf=true` with no `.gitattributes` previously let `src/data/__snapshots__/workshopCategories.test.js.snap` show up as locally modified with zero actual content difference — a Windows line-ending stat-cache quirk. Fixed with a repo-root `.gitattributes` (`* text=auto eol=lf`), pinning line endings for all text files regardless of platform/`core.autocrlf`; confirmed via `git add --renormalize .` producing no changes and the snapshot file no longer showing as modified.
**Resolved in:** [#27](https://github.com/luplows/tower-workshop-paths/pull/27).

**OQ-17. Show the cheapest next Workshop upgrade as a ranked list (Upgrade Path page)**
As a player, I want a page that tells me the single cheapest thing to buy next, so that I have a starting recommendation before the full priority-weighted algorithm (OQ-2) exists.
A new "Path" section renders `UpgradePath`, which ranks every not-yet-maxed Workshop upgrade purely by the coin cost of its next single level, cheapest first — no priority ratios, per the user's explicit "for now, just focus on lowest cost" scope. Deliberately **not** a third entry in `ModeTabBar` alongside Upgrade/Enhance: that toggle mirrors the game's own buttons, and there's no "Path" screen in-game, so Path lives behind its own top-level `AppSectionTabs` control ("Input" vs "Path") in the header, and `ModeTabBar`'s Upgrade/Enhance toggle only renders within the "Input" section. The pure ranking logic (`getCheapestNextUpgrades`, `src/utils/cheapestNextUpgrades.js`) reads current levels from the same `workshopLevels` `localStorage` key the Upgrade screen uses, and is unit-tested independently of the UI. Upgrades whose current level has no valid cost data (see OQ-1's new finding) are listed separately as "cost data unavailable" rather than silently omitted or mis-ranked. Enhancements were out of scope for this page at the time — it was specifically the *Upgrade* path (later extended to include Enhancements too, see OQ-29). Next per the user: OQ-18 (buy directly from this list), then folding in priorities (OQ-2).
**Resolved in:** [#31](https://github.com/luplows/tower-workshop-paths/pull/31).

**OQ-19. Let the Path list include the same upgrade multiple times**
As a player, I want the Path list to show an upgrade's 2nd, 3rd, etc. next levels too when they're still cheaper than other upgrades' first next level, so that the ranking reflects the true cheapest sequence of purchases, not just each upgrade's single next step.
`getCheapestNextUpgrades` (OQ-17) now simulates a full buy-out step by step — at each step, "buying" whichever not-yet-maxed upgrade currently has the cheapest next single level, then re-evaluating with that upgrade's level advanced by one (a simulation for ranking purposes only; it never touches the caller's actual entered levels) — rather than only ever considering each upgrade's first next level once. Capped at 50 total rows (`DEFAULT_ROW_CAP`, overridable via a `rowCap` option) since simulating every remaining level of every upgrade would be both enormous and not useful this far ahead; a firmer answer to "how many to buy at once" belongs to OQ-7 (batch buying), which this doesn't attempt. `unknownCost` (see OQ-1) now also catches an upgrade that starts out fine but hits its cost-data ceiling only after some simulated purchases, not just one whose *currently entered* level is already past it — reported once, at the level it got stuck. Caught by testing: `UpgradePath`'s list rows were keyed by upgrade name alone (`key={entry.name}`), which silently breaks once the same name can appear more than once — fixed to key by name + level.
**Resolved in:** [#32](https://github.com/luplows/tower-workshop-paths/pull/32).

The cost-ascending and "climbs one level at a time" checks are invariant-based rather than hardcoded row-by-row, so they stay meaningful (and don't need updating) if `tower-idle-toolkit`'s underlying cost data changes.

**OQ-7. Implement batch buying**
As a player, I want the recommended buy order to reflect how I actually purchase in-game (multiple levels at once), so that the steps match real button presses.
`getCheapestNextUpgrades` (OQ-17/OQ-19) now ranks by batch cost, not single-level cost: 100 levels at a time for a Workshop upgrade with more than 1000 max levels, 10 for one with at least 10, or 1 for one with fewer than 10 max levels in the first place (Multishot Targets, Bounce Shot Targets, Orbs — caught in review; missed in the first pass) — see `Project-Outline.md`. Still Workshop-only (Enhancements aren't batched). **Correction from the original framing:** the game doesn't actually require buying in these batches — single-level purchases remain available in-game too — this tool just always expresses the Path list's recommendations in these fixed batch sizes for practicality; `README.md`, `Project-Outline.md`, and the code comments were reworded to not overstate this as a game restriction. Each ranked entry gained a `levels` field (the batch size actually used) alongside `currentLevel`/`nextLevel`, which now jump by that many levels instead of always by 1. **Resolved the open partial-batch question:** a batch shrinks to whatever's left when fewer than a full batch remain before max level (e.g. an upgrade 4 levels from max with a 10-level batch size buys those final 4) — the only case a batch is ever shrunk. If any level within a (max-trimmed) batch has no valid cost data, the whole batch is refused and the upgrade lands in `unknownCost` rather than pricing a partial one, since a real near-max partial batch and a data gap aren't the same situation. Confirmed the ranking math genuinely changes, not just presentation: at level 0, the previous single-level cheapest-first order (led by several upgrades tied at cost 30) is replaced by one led by Multishot Targets' 1-level batch (cost 450, since its max level is only 7). Rewrote `cheapestNextUpgrades.test.js`'s existing scenarios for batch semantics, added dedicated tests for the sub-10-max-level batch size, partial-batch trimming, and batch-refused-on-data-gap, and updated `UpgradePath`'s tests (unit, component, e2e) to match.
**Resolved in:** [#38](https://github.com/luplows/tower-workshop-paths/pull/38) (tracked since [#28](https://github.com/luplows/tower-workshop-paths/pull/28)).

**OQ-22. Add a "Clear" button to zero out entered levels**
As a player starting over (a fresh game save, or just wanting to re-enter everything cleanly), I want a way to reset my entered levels back to zero without hand-clearing every input, so that starting over isn't tedious.
A new `HeaderMenu` component (`src/components/HeaderMenu.jsx`) adds a "⋯" overflow button in the header, next to the Input/Path toggle (`AppSectionTabs`) — a deliberately separate control so that toggle stays the visible, frequently-used primary navigation while Clear lives in the menu, with room for future secondary actions. Confirming removes both the `workshopLevels` and `enhancementLevels` `localStorage` keys in one combined action (not split per-mode/per-tree, per the decision recorded here previously) and bumps an in-memory `resetNonce` in `App.jsx`, passed as the `key` prop to `WorkshopInputs`/`EnhancementInputs`/`UpgradePath` — forcing whichever is currently mounted to remount and re-read the now-cleared `localStorage`, without a full page reload. Navigation state (selected mode, tree tab, section) is untouched, only entered levels reset.

**OQ-26. Condense and truncate large/fractional coin costs in the Path list**
As a player, I want costs shown the way the game itself displays large numbers, so that they're readable and match what I'd expect to see in-game.
Confirmed the fractional costs noticed in the Path list aren't a data bug: `tower-idle-toolkit`'s own per-level `coins` values are genuinely non-integer from around level 50-100 onward for most Workshop upgrades (e.g. Damage level 90 costs 65467.5162084332), not just an artifact of summing batches (OQ-7). A new `formatCoins` util (`src/utils/formatCoins.js`) replaces `UpgradePath`'s plain `toLocaleString()` display: condenses with a suffix once a cost reaches the thousands — k, M, B, T, then alternating-case q/Q (quadrillion/quintillion) and s/S (sextillion/septillion), up to O (octillion, 10^27 — comfortably above the largest cost currently in the data, ~4.56 quintillion) — and truncates (never rounds) to 2 decimal places, dropping a trailing ".00" or trailing zero (e.g. `2.98k`, `137.45M`, `2.5B`, `30`). Truncation applies below the thousands tier too, since costs are fractional well before reaching a suffix.
**Resolved in:** [#43](https://github.com/luplows/tower-workshop-paths/pull/43).

**OQ-29. Add Workshop Enhancements to the Path list**
As a player, I want the Path list to recommend Enhancements alongside Workshop upgrades, so that it's a single ranked source of "what's cheapest right now" instead of only covering half of what I might buy.
Blocked at first on missing data: no per-level Enhancement cost table existed anywhere in the codebase or in `tower-idle-toolkit` (only category names, max levels, and the value formula did, from OQ-14). Resolved by transcribing the community sheet's "Workshop Enhancement Prices" tab (see `README.md` for credit) into a new `src/data/enhancementLevels.js` — 18 plain arrays (index = level, value = coins to advance to the next), parsed exactly via `BigInt` arithmetic from the sheet's own condensed values (e.g. "5.04 B") rather than floating-point multiplication, to avoid compounding extra rounding error on top of what the sheet already carries (roughly 3 significant figures, not Workshop's exact-to-the-coin precision — see OQ-30). Every one of the 18 arrays' lengths was cross-checked against `enhancementCategories.js`'s `quantity` at generation time and matched exactly.
`getCheapestNextUpgrades` (`src/utils/cheapestNextUpgrades.js`) now takes `{ workshopLevels, enhancementLevels }` instead of a single flat map, and builds cursors from both `WORKSHOP_CATEGORIES`/`WORKSHOP_LEVELS` and `ENHANCEMENT_CATEGORIES`/`ENHANCEMENT_LEVELS` into one combined greedy simulation — same algorithm, same cost-only/no-priority scope (OQ-17), same batch-refused-on-missing-data handling (OQ-7). Enhancements always use a 1-level batch (a real game rule, per the reminder that prompted this), never Workshop's 10/100-level batching. Since several names collide across the two systems (e.g. "Damage", "Health" both exist as a Workshop upgrade and an Enhancement category), every `ranked`/`unknownCost` entry now carries a `source` (`'workshop'` or `'enhancement'`) and cursors are keyed by `source:name` internally — name alone is never enough to identify an entry. `UpgradePath` routes a purchase to the matching `workshopLevels`/`enhancementLevels` `localStorage` state by `entry.source`, and displays an Enhancement row as "{name} +" (e.g. "Damage +") — the game's own naming convention for Enhancements, confirmed via the same community sheet's own "Workshop +" row label — rather than an invented badge, so it's never confused with a same-named Workshop row at a glance. That same "{name} +" convention was then also applied to the Enhance input screen itself (OQ-14): `UpgradeLevelInput` gained a `nameSuffix` prop, threaded through `WorkshopCategoryPanel`/`CategoryLevelInputs`, that `EnhancementInputs` sets to `" +"` and `WorkshopInputs` leaves empty — display-only, so the underlying storage/lookup key (`upgrade.name`) stays the clean name everywhere, only the rendered `<label>` (and its accessible name) changes. Enhancement/unlock gating (the per-tree cumulative-spend thresholds and the "Workshop Enhancements" Lab) is explicitly out of scope for this pass, per the user's "same temporary rules" — an Enhancement can be recommended here even if the player hasn't actually unlocked it yet, same as Workshop's OQ-4/OQ-5 gaps.
**Resolved in:** [#44](https://github.com/luplows/tower-workshop-paths/pull/44).

**OQ-28. Confirm before under-buying a repeated upgrade's later row**
As a player buying a row for an upgrade that also appears earlier in the Path list (OQ-19 repeats), I want to be warned that buying just this row skips those earlier occurrences, so that I don't end up with fewer levels than the row's own "Lv X → Y" seems to promise.
Previously, buying any row only ever added that row's own batch to the real entered level — correct for a row's *first* occurrence, but silently short for a later one, since the row's `currentLevel` is a simulated value that assumes every occurrence before it was already bought. `UpgradePath` now checks, on click, whether the same item (same name *and* source — OQ-29) appears earlier in the ranked list; if so, it shows a confirmation (`role="alertdialog"`) instead of buying immediately, condensed to a single question — "Buy all {name} upgrades to reach Lv {level} ({total cost})?" — with just two buttons, right-aligned: "Buy all" (green, adds every earlier occurrence's `levels` too, landing exactly at this row's `nextLevel`) and "Cancel" (red). An earlier iteration also offered a "Just this batch" option and showed the batch count on the "Buy all" button; both were dropped as redundant once the dialog itself made the full-buy consequence clear. A row with no earlier occurrence of its own item still buys immediately, no dialog. Both buttons (and the Clear-all-levels dialog's) share a hover state that inverts to a solid fill, matching the Buy button's own hover.
**Resolved in:** [#43](https://github.com/luplows/tower-workshop-paths/pull/43).

**OQ-31. Implement the Workshop Enhancements Lab unlock gate**
As a player, I want the Path list to respect the fact that no Enhancement is purchasable at all until the one-time "Workshop Enhancements" Lab is bought, so that it never recommends an Enhancement I couldn't actually buy yet.
The Lab's cost (5B coins flat, confirmed) was the only missing piece — modeled in `getCheapestNextUpgrades` as its own candidate, `source: 'lab'`, a single level (0 → 1), always a 1-level batch, rather than a special-cased boolean: while a new `enhancementLabLevel` parameter is below 1, the Lab is the *only* Enhancement-related candidate in the whole simulation — every Enhancement category is excluded entirely, not shown as locked or unavailable, matching "no Enhancement is purchasable at all" literally. Once `enhancementLabLevel` reaches 1, the Lab candidate disappears and every Enhancement category becomes ordinary again, same as before this story. `UpgradePath` persists the Lab's state under a new `enhancementLabLevel` `localStorage` key (0 or 1), routes a `source: 'lab'` buy there via `applyBuy`, and displays it as plain "Workshop Enhancements Lab" — no "{name} +" suffix, since it isn't itself an Enhancement category. `HeaderMenu`'s "Clear all levels" now also re-locks the Lab (removes `enhancementLabLevel`), and its confirmation text says so. The per-tree cumulative-spend gate (the other half of OQ-6) is still open — this resolves only the single global Lab gate.
**Resolved in:** [#45](https://github.com/luplows/tower-workshop-paths/pull/45).
