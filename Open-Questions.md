### Project health and workflow

Not player-facing features, but they decide how safely and cheaply everything above can be built. OQ-40 and OQ-44, which closed the appearance gaps that removing the pre-merge visual-inspection gate opened, are resolved; see `Completed-Questions.md`.

**OQ-42. Add automated, merge-gating review to pull requests**
As someone working on this project, I want every PR to get an adversarial read of its diff before it merges, so that a green CI check isn't the only thing between a change and `main` — and so that an agent handed a task can be confirmed to have followed the whole defined process, every time.
`.github/workflows/review.yml` now exists and runs on every PR, but it has never once completed a review (see **Built, not yet working** below). Since the visual-inspection gate was removed, CI is the sole quality signal on every PR, and CI only knows what the tests already assert; it cannot flag a plausible-looking bug that no test covers, nor a skipped step in the project's own workflow.

**Decided:**
- **A GitHub Action, not a pre-push step.** The requirement is that review be unskippable. A pre-push step only runs when someone remembers, and agent sessions only run it if their prompt happens to say so.
- **It gates the merge**, as a required status check.
- **It reviews process compliance, not just code** — the `CLAUDE.md` rules about doc updates, OQ numbering, `Completed-Questions.md` conventions and commit granularity. Process review may be worth more here than bug-hunting: the miss that made #77 necessary was a process miss, not a code one.
- **Docs-only PRs are reviewed too**, but through one path-filtered workflow rather than a second mechanism: code *and* process criteria when the diff touches app code, process criteria alone when it doesn't.
- **Actions minutes are not a constraint** — this is a public repo, so standard runners are free and unlimited. The budget worth watching is Claude usage per review, given the high volume of small PRs here.
- **Independence comes from context isolation, not model diversity.** A reviewer that shares the author's *context* knows what the change intended and so can't see that the diff doesn't do it; a reviewer that merely shares the author's model can still re-derive from the artifact. An Action supplies that isolation structurally — fresh runner, no authoring session, just the diff and the repo. The real decorrelating mitigation for shared priors is giving the reviewer explicit written criteria, which is what the process checklist above is. Running review on a different model from the usual author is a cheap optional hedge, not a substitute.

**Decided — what clears a finding.** No dismissal mechanism at all: the check simply re-runs on every push, so the only way through is to change the diff. Severity tiers were rejected because they put the blocking decision inside the same system being checked (everything can be marked a nit and the gate becomes theater), and an acknowledgement protocol was rejected because it lets an agent clear a finding with words rather than work. Retries are **bounded at 2 rounds** — deliberately tight, so that the gate can be observed actually firing while it is new — after which the agent states the disagreement on the PR, applies a `review-blocked` label and escalates to a human. A blocked PR **blocks its own merge only**; the agent is free to move on to other work rather than idling.

**Decided — circuit breaker.** Once **5 open PRs** carry `review-blocked`, something systemic is wrong (bad checklist, bad reviewer, bad prompts) and spawning more agents only multiplies it. Two layers, deliberately: the SessionStart hook counts labelled PRs and emits a banner into the session before the agent starts work (automatic, but advisory — nothing can hard-stop an agent the way branch protection hard-stops a merge), and the review workflow itself fails on every PR while the breaker is tripped (genuinely enforced — agents may keep working, but nothing lands). Two implementation notes worth not rediscovering: GitHub's `/search/issues` API is **not available to session tokens** ("sessions are bound to..."), so the hook must use the repo-scoped `/repos/{owner}/{repo}/pulls` endpoint and filter labels client-side; and the enforced layer must exempt the PR that fixes the jam (a `breaker-override` label, or auto-exempting workflow-only diffs), or it becomes a trap escapable only by admin merge.

**Built, not yet working.** The workflow, the `review-blocked` labelling, the 2-round bound and both breaker halves shipped non-enforcing in #82, with `REVIEW.md` and the PR template in #81. Everything around the review runs correctly — the breaker queries labelled PRs on a runner, the credential guard detects a missing secret and skips cleanly, the verdict step treats a missing verdict as inconclusive. The review itself has never completed: the Claude Code Action returns `401 OAuth access token is invalid`, retried 10 times, after ~2s at zero cost. Three things were found along the way and are worth not rediscovering:
- `github_token` must be passed alongside `claude_code_oauth_token`, or the action attempts GitHub App authentication (an OIDC exchange) first and 401s before reaching the model ([action#721](https://github.com/anthropics/claude-code-action/issues/721)). Necessary but, here, not sufficient.
- The action suppresses its own error text by default, so any failure reads as a bare `is_error: true, total_cost_usd: 0`. `show_full_output: true` is the only way to see the real message, and it prints model output into what is a public log here — a real cost to weigh before trusting this as a merge gate.
- The review step carries `continue-on-error` so a non-enforcing check does not paint every PR red, which would train everyone to ignore the signal before it ever becomes a gate. **That must come off when `REVIEW_ENFORCING` goes on** — a gate that cannot fail is not a gate.
The truncated-paste explanation is now ruled out: a second, freshly generated token was pasted and produced the identical 401, so this is [action#1614](https://github.com/anthropics/claude-code-action/issues/1614) -- open, no maintainer response, no workaround. The review step is therefore **gated behind a `REVIEW_ENABLED` repository variable, default off**. That is not merely tidiness: with `continue-on-error` set, a review that failed completely reported a **green** check, and a signal meaning "reviewed fine, or did not run at all" is worse than a red one. A step that always runs now states in the log that no review happened. Turning it back on means either upstream fixing #1614 or switching to `ANTHROPIC_API_KEY`, which reintroduces the separate billing stream the OAuth route was chosen to avoid.

**Enforcement, routed around the broken piece.** `.github/workflows/review-gate.yml` splits the gate from the judgement, so no part of the enforcement calls Claude. A PR opening or gaining a commit sets a `review/agent` commit status to pending; a reviewer agent — a fresh session with no authoring context — reviews the head commit and comments with a marker (`<!-- agent-review head=<40-char-sha> verdict=pass|fail -->`); the workflow reads that marker and sets the status. Requiring `review/agent` in branch protection is what makes it a gate. Three properties worth keeping: a commit status has no self-approval restriction, unlike a PR review, so a single-account project can gate itself; a new commit resets the status to pending, making "no dismissal mechanism" a platform guarantee rather than a convention; and forgetting to run the reviewer leaves the status pending, so the PR cannot merge — the gate fails safe rather than silently passing. The marker is only honoured from a commenter with write access (anyone can comment on a public repo) and only when its sha matches the current head (a verdict about an older commit says nothing about this one).

**Confirmed enforcing, and what the first real runs cost to learn.** `review/agent` is now a required status check and the gate has held a PR shut for the first time (#93). The reading that proves it: on a PR with CI green and only `review/agent` pending, `mergeable_state` must be `blocked`. When it was not yet required the same state read `unstable`, because `unstable` means a *non-required* check is outstanding — a distinction worth keeping as the standing regression test, since the required-check entry silently went missing once between being set and being checked the next morning. Two operational findings from getting there, both about the reviewer rather than the gate:
- **A spawned reviewer needs GitHub credentials, and does not reliably inherit them.** Sessions failed by hanging on a permission question nobody was there to answer, and twice by being unable to read a public PR body or post at all. Pre-authorising `add_repo` with `access: "push"` via `extra_allowed_tools` on the spawn is what fixed it. A reviewer that cannot comment cannot clear the gate, so this is part of the gate's reliability, not a detail of how it is invoked. Relatedly: a spawned reviewer must be told not to ask questions — there is no human attached to it, so `AskUserQuestion` is not a degraded path but a hang.
- **The workflow only saw comment creation, not edits.** A reviewer that posted its review and edited the marker in four minutes later was ignored: the run fired against the markerless body, concluded `skipped`, and no event followed. The PR then sat pending with a valid, correct verdict visible on it — worse than a plain rejection, because it reads as a broken gate rather than a missed marker. Fixed by subscribing to `[created, edited]`, which costs nothing in safety since the write-access and current-head guards both still apply; the reviewer prompt also now asks for the marker in the initial post.

**Spawn prompts live in files, and are read end to end before use.** [`.claude/reviewer-prompt.md`](.claude/reviewer-prompt.md) and [`.claude/worker-prompt.md`](.claude/worker-prompt.md) exist because an improvised prompt is never reviewed: the one that launched the OQ-43 worker asserted `review/agent` was already a required check and that its PR would be blocked, neither of which was true then. The worker behaved correctly on the strength of a claim nobody had checked. The sharper lesson came later — a spawn prompt that gains one fix per failed run can end up injection-shaped. After three reviewer sessions failed on credentials and one hung on a question, the prompt had grown instructions to hunt for tokens on disk *and* to raise questions with nobody, and the next reviewer correctly refused the task as suspicious. Each addition was locally reasonable; the assembled prompt was not, and nobody had re-read it whole. The fix is to remove what is actually suspicious, never to add reassurance that the task is legitimate — that sentence is what a real injection would say, and a reviewer trained to accept it has lost a defence worth keeping.

**Still open — who merges once the verdict lands.** `CLAUDE.md` now says the author agent squash-merges its own PR when CI is green and `review/agent` passes. That assigns the job to a session which may no longer exist by the time the condition becomes true: review is minutes to tens of minutes behind the push, and a worker spawned for one story finishes long before its verdict arrives. #92 sat merge-ready with nobody responsible for noticing. The current fallback is that an orchestrator happens to check, which is not a mechanism. Options: let the reviewer merge after passing (cheap, but collapses the separation between judging a PR and acting on that judgement that the rule deliberately establishes), have the author schedule its own wake-up before exiting (keeps the separation, but fails silently if the session dies), or run a periodic sweep for PRs that are green, verdict-passed and still open (robust, and the only one that catches a PR whose author is gone).

**Still open — the checklist itself.** "Read `CLAUDE.md` and check compliance" is too vague to be auditable; a miss could be a bad rule or a bad reading and there would be no way to tell. The review needs an explicit enumerated checklist, which is also the real mitigation for shared priors between author and reviewer. Also worth instrumenting from day one: log every verdict, and after ~20 PRs check the block rate — if it is zero, the check is latency rather than a gate.

**OQ-46. Walk the owner through a batch of changes, roughly every 10 PRs**
As the person this project belongs to, I want to be walked through what has actually changed after roughly every 10 merged PRs, so that dropping the per-PR human gate doesn't cost me the mental model of my own app.
Removing the pre-merge visual-inspection gate traded per-PR human attention for automated guards — the screenshot assertions from OQ-40 and the palette work in OQ-44 (both in `Completed-Questions.md`), plus the agent review gate in OQ-42 above. Those guards are all *regression* detectors: they compare the app to what it was, and they pass when a change is self-consistent. None of them can tell the owner that the tool now does something he never pictured, or that ten small, individually-reasonable changes have added up to a different product. This story puts the human read back in at a tenth of the frequency — a batch walkthrough rather than a per-change gate. Three things it should cover: **UI changes**, shown rather than described (the baselines in `e2e/__screenshots__/` are the obvious raw material — a before/after of every baseline that moved across the batch); **functionality changes**, a short recap of what the tool does now that it didn't at the last checkpoint; and **docs changes**, what moved in `README.md`, `Project-Outline.md`, and the OQ files, including which stories were resolved.
**Explicitly not a gate.** It does not block merges and does not stop agents — same call as OQ-42's blocked-PR handling, and for the same reason: a review that halts all progress while it waits for a human stops being run. If the walkthrough finds something wrong, that becomes an ordinary OQ like anything else.
**Open questions:** what counts to 10 and where the count lives — merged-PR count since the last checkpoint is the intent, but something has to hold the marker and raise the flag (a scheduled workflow counting merges since a tag, a pinned issue, or the `SessionStart` hook, which already counts `review-blocked` PRs and so has the machinery); what form the walkthrough actually takes (an issue with embedded before/after images, a generated page, or an interactive session that presents it and takes questions) — the images make a static artifact attractive, but "quick recap" implies something conversational; and whether "roughly 10" should instead be time-based, since 10 PRs could be a week or a month depending on how hard the project is being pushed.
