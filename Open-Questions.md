# Open Questions / In Progress

Outstanding tasks and unresolved questions for the project. See `Project-Outline.md` for goals and definitions.

- **Verify per-level cost accuracy**, not just max levels: only `quantity` has been spot-checked/corrected so far (see below). The buy-order algorithm consumes `WORKSHOP_LEVELS`' actual `cash`/`coins` cost figures directly, so an unverified stale cost there would produce a wrong recommendation even after quantities are fixed — this is more consequential than the max-level task and hasn't been started.
- **Task (in progress):** refresh each upgrade's `quantity` (max level) against actual in-game values. Current-level inputs are hard-capped at `quantity` (`UpgradeLevelInput`, via `clampLevel`), so a stale-too-low value incorrectly blocks valid entries until corrected. Corrections are applied via `WORKSHOP_QUANTITY_OVERRIDES` (`src/data/workshopQuantityOverrides.js`) rather than editing the third-party package. Confirmed so far: Rend Armor Chance (299), Health (6000), Health Regen (6000), Recovery Amount (300), Max Recovery (500). The rest of the ~40 upgrades still use `tower-idle-toolkit`'s original (possibly stale) values.
- **Guard against upstream structural drift.** A Vitest snapshot test (`workshopCategories.test.js`) captures the current name/quantity of every upgrade in every category, so a `tower-idle-toolkit` update that silently adds/removes/reorders an upgrade or changes a quantity fails CI with a reviewable diff instead of passing unnoticed. Updating the snapshot (`vitest -u`) should always be a deliberate, reviewed choice — check whether it reflects a real, current game change (and needs a `WORKSHOP_QUANTITY_OVERRIDES` entry) or just an upstream data revision to accept as-is.
- Production bundle is ~2.4MB minified, mostly `tower-idle-toolkit`'s bundled game data (labs, cards, bots, etc. we don't use) — worth revisiting with code-splitting or a narrower import once the app has more real usage to justify the effort. Not currently blocking anything.
- **Enhancements data — mostly resolved.** Found via a community Google Sheet (see `Project-Outline.md` for the full mechanic and per-tree unlock table): per-level costs for all 18 categories, and the cumulative-spend thresholds that gate 5 of each tree's 6 categories. Two values remain unknown: the cost of the "Workshop Enhancements" Lab that gates the whole system, and the per-level values of the parallel "Enhancements Discount" Lab — left as open gaps for now rather than digging further.
- UI polish: add a proper title/header to the screen, and color the three category tabs to match their in-game trees — Attack (blue), Defense (red), Utility (yellow).
- **Implement the buy-order algorithm itself.** The scoring formula is designed and hand-verified (see `Project-Outline.md`), and the current-level input UI exists, but there's no code yet that actually computes a recommended buy order from those levels + costs + priorities — this is the tool's core feature and still unbuilt.
- Need to source/define the **predefined community-recommended priority order** mentioned as a goal in `Project-Outline.md` — nothing researched yet.
- The phone-mimicking UI has only been checked in a desktop browser at a fixed width — need to verify actual behavior/usability on a real mobile/touch device, which is the realistic use case (checking the tool while playing).
- **Design and implement discount-adjusted costs.** Confirmed in `tower-idle-toolkit`: three per-category Labs — `Workshop Attack Discount`, `Workshop Defense Discount`, `Workshop Utility Discount` — each level 0-99, giving 0.5% off that category's Workshop costs per level (up to 49.5% at max), via `LabValues['Workshop Attack Discount'](level)` etc. Needs: (1) a new input for the user's current level in each of the 3 discount labs, (2) applying the resulting discount to every cost the buy-order algorithm and any displayed cost use. No equivalent "Enhancement Discount" lab exists in this data source (ties into the Enhancements data gap above).
- **Design and implement upgrade-unlock gates.** Confirmed in `tower-idle-toolkit`: `ATTACK_UNLOCKS` / `DEFENSE_UNLOCKS` / `UTILITY_UNLOCKS`, each an ordered list of `{ name, cost, upgrades[] }` groups (a free "Default" group, then paid groups that gate specific upgrades behind a one-time coin cost — e.g. Utility's "Upgrade Chances" group costs 800 coins to unlock the three "Free X Upgrade" upgrades). Needs: (1) a way for the user to mark which unlock groups they've already purchased, (2) the buy-order algorithm must exclude not-yet-unlocked upgrades from consideration. Open design question: should purchasing an unlock itself compete as a priced item in the buy-order (spending coins to unlock vs. buying an upgrade level), or be treated as a separate, manual, one-off step outside the main algorithm?
- **Enhancements current-level input UI — done; gating still open.** A top-of-screen "Upgrade"/"Enhance" mode tab bar (matching the in-game button labels, `ModeTabBar`) switches between the existing Workshop upgrade screen and a new Enhancements screen (`EnhancementInputs`, `src/data/enhancementCategories.js`) with the same three-tree tab layout and per-item level input, persisted separately (`enhancementLevels` in `localStorage`). The bottom category tabs on both screens read just "Attack"/"Defense"/"Utility" (shortened from e.g. "Attack Upgrades" to avoid text wrapping). The 18 categories and their unlock-threshold values (`unlocksAt`) are hard-coded from `Project-Outline.md`'s table since `tower-idle-toolkit` has none of this data; levels are entered with no enforced max, since no max-level source exists yet for Enhancements (unlike Workshop's `quantity`). Since there's no in-game way to see an Enhancement's current *level* (only its resulting value), the Enhance screen also shows a computed value (`src/utils/enhancementValue.js`, `value = (level × 0.01) + 1`, e.g. "1.40×") next to each level input, letting the user cross-check their entered level against what they can actually see in-game; Workshop upgrades intentionally show no such value, since too many other multipliers apply there for a raw computed value to be meaningful. Still open, unchanged from before: the buy-order algorithm needs to track running per-tree Enhancement spend (not just current levels) against those thresholds to know what's currently purchasable, and must treat the whole Enhancement system as locked until the "Workshop Enhancements" Lab is completed — that Lab also has no input yet. Unlike Workshop's one-time unlock purchases, an Enhancement category unlocks once *cumulative coins spent on that tree's other enhancements* crosses a threshold (see `Project-Outline.md`).
- **Design and implement batch buying.** The buy order should recommend Workshop upgrade purchases in batches (100 levels at a time for anything with >1000 max levels, 10 otherwise — see `Project-Outline.md`); Enhancements are always 1 at a time, not batched. Unresolved: how the score formula's "next cost" should be computed for a batch (sum of N consecutive per-level costs from `WORKSHOP_LEVELS` rather than a single level's cost); how to handle a partial batch when fewer than N levels remain before max level.
- **Watch for spurious `.snap` file "modified" status on Windows.** `core.autocrlf=true` is set with no `.gitattributes` pinning line endings, and `src/data/__snapshots__/workshopCategories.test.js.snap` has shown up as locally modified (`git status`) with zero actual content difference (`git diff`/`git hash-object` confirm an identical blob to what's committed) — a Windows line-ending stat-cache quirk, not real snapshot drift. Harmless so far (`git checkout -- <file>` clears it), but if it starts obscuring a *real* snapshot change or recurs often enough to be annoying, fix it permanently with a `.gitattributes` entry pinning `*.snap` (and likely other text files) to `eol=lf`.
- **Follow-on feature (not started): full workshop recommendation from lifetime coins.** Let the user input two aggregate numbers — lifetime coins earned and coins spent on Labs — instead of (or in addition to) manually entering every upgrade's current level, and have the tool simulate the entire recommended buy order from zero up to that coin budget (lifetime coins minus Labs spend). This is the same core scoring/buy-order engine run to completion rather than one step at a time, so it should reuse that engine rather than duplicate its logic. Offer two output views computed from the one underlying purchase sequence: a granular step-by-step list (e.g. 100 Health, 100 Regen, 100 Health, ...) and a simplified rollup grouping consecutive/total purchases per upgrade (e.g. 5000 Health, 5000 Regen) — the simplified view should be a group-by of the granular sequence, not a separate calculation, so the two can't drift out of sync. Blocked on the core buy-order algorithm itself being implemented first (see above), and since a from-zero simulation can't defer decisions the way manual level entry currently does, it also forces resolution of the still-open discount-lab, unlock-gate, batch-sizing, and Enhancement-gating design questions above before it can be built.
